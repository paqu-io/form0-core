# BuildingPlan version-2 record example

Two staggered 5 m × 3 m rooms share one 2 m physical piece. Their combined 8 m straight run is divided into 3 + 2 + 3 m owners with consistent adjacency. Each owner has one geometry span and two canonical sides. The shared piece hosts one 0.9 m door.

- [schema.json](schema.json) contains authored custom definitions and configuration references.
- [record-output.json](record-output.json) contains the canonical submitted record.
- [semantic-output.json](semantic-output.json) decodes that record into metric objects.
- [create-example.js](create-example.js) constructs the fixture through domain operations.

The files describe a valid collected layout, not evidence from a running UI session.

## Ownership and editing

The editor retains floor → room → column/beam/object/wall → door/window, with ordinary Add, Edit, Save and Cancel. A child Save accepts into its parent draft. Shared physical questions are edited through a room wall row. Protected inline system sections are generated by the compiler; custom material and finish fields remain authorable and use safe copy-on-split policies.

```text
record.form_values
└─ floors[]
   ├─ physical_walls[]
   │  ├─ geometry and accepted physical answers
   │  ├─ wall_sides[] → canonical surface answers
   │  ├─ doors[]
   │  └─ windows[]
   └─ rooms[]
      ├─ polygon and room answers
      ├─ columns[], beams[], objects[]
      └─ walls[] → side references and editor projections
```

Room projections are excluded from submission. Canonical wall/side answers are stored once. There is no predefined Observations collection; an authored inspection repeatable has ordinary independent record semantics.

## Geometry and inheritance

The `room_vertices`, `wall_geometry` and `*_model` fields contain JSON strings with version-2 identities and metric geometry. Each wall's `segments` array contains exactly one geometric span; segments do not own properties, overrides or defaults. Coordinates and identifiers are managed internally.

The fixture's explicit floor defaults supply thickness and wall height. General authoring can instead route declared scalar/choice fields with `building_plan.property`, one `inherit_to` descendant, optional `applies_to` filters and physical-wall or wall-face ownership. Explicit destination overrides take precedence; resetting restores live inheritance. Storey height does not implicitly supply wall height.

A physical-property edit affects the complete addressed piece. Surface answers belong to a canonical side, including an uncovered outside side. Attaching a room preserves existing outside answers. Exposure is derived from room coverage; both sides covered is interior, including an internal partition in one room.

Automatic labels identify the canonical physical owner in both the system field and every room’s canvas view. A retained owner keeps its label; new related pieces receive suffixes such as `W3.1`. Other owners are not renumbered. Explicit labels remain editable. The lower-left piece in the initial fixture is `W3.2`; the earlier room-order canvas caption was W4.

A downward jog of this lower-left piece fits its return to Room 2’s existing left-wall band. Room 2’s outline remains fixed, and the return shares the existing physical axis over the new coverage. Upward and downward reversals use the same junction rules. Clearance, pins, opening recovery and answer-transfer confirmation remain active.

## Transactions and questions

Split divides physical ownership, retaining the original owner at its reference end and recording lineage. Openings retain their identities, dimensions and world positions while host offsets are rebased. Rejoin requires collinearity, equal adjacency, compatible override intent and compatible corresponding surface answers. Explicit cuts survive automatic cleanup.

Explicit custom wall-bound answers and collections default to `on_split: 'confirm'`. Confirmation authorizes copying, without allocation or costing. Calculations are recomputed and inherited values are resolved for each resulting piece.

Internal decisions use the managed question registry directly. They are not generated into editable `events.code`. A topology operation that changes inherited physical values offers new defaults, preservation through explicit overrides or cancellation. `editingPolicy.inheritedChangePolicy` defaults to `ask`; only CLI Settings exposes `ask`/`apply`. Changing the preference alone changes no record or history.

Text and numeric controls retain ordinary change/blur behavior. Internal completion checks for changed, valid values; no Done/Enter action is introduced. Save finishes the focused edit and settles pending decisions. Cancel does not force a new blur question. Geometry, remapping and accepted decisions form one Undo entry and remain inside their initiating nested editor scope.

A division or move through an opening returns `opening_cut_requires_confirmation`, with exact `openingIds` and opening labels. Retry the same operation with the confirmed `removeOpeningIds`. Cancellation changes nothing. A stale or unrelated removal list is rejected. The optional canvas `confirmOpeningRemoval(issue)` callback retains the existing recovery presentation.

## Regenerate and verify

From the core checkout:

```bash
node examples/building-plan/generate.mjs
node examples/building-plan/verify.mjs
```

Generation changes only this example's three JSON files. Verify them together with the matching implementation. Existing version-1 development schemas and records are rejected clearly; this example supplies no migration, export adapter, reform integration, costing logic or quantity builtin.

A thickness-only shoulder is derived material geometry, not another physical wall. Obsolete automatic adjacency stations coalesce only when answers and coverage agree. Deliberate cuts survive; retained straight answer boundaries are available to Rejoin.

CLI Settings → Building Plan Editing → **Copy custom answers automatically** controls `editingPolicy.copyCustomAnswersAutomatically` (off initially in CLI/core, on in React/Native). It authorizes future copies of explicit custom answers and nested rows. Inherited-default reviews retain their separate ask/apply setting. Changing a preference does not change the record or history.
